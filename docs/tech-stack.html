家計ダッシュボード3 — 仕様・設計・技術構成

夫婦の家計を月単位で集計・可視化するWebアプリ。Cloudflare Workers 上で API と SPA を1つの Worker から配信し、データは D1 に置く。同じロジックが TypeScript と Python の2言語で二重に実装されているのが最大の特徴。

1. このアプリは何をするものか

夫婦2人の家計を 月（YYYY-MM）単位 で記録し、KPI・グラフ・貯蓄目標として見せる。データの最小単位は「ある月の、あるカテゴリに、いくら使ったか」の1行。

ダッシュボード

features/dashboard/Dashboard.tsx

選択した月の KPI（収入・支出・貯金・純資産など）と前月比較。

  • 数値は必ず product-card の中に置く
  • 前月が無い月は比較を出さない

グラフ

features/charts/ChartsTab.tsx

支出の円グラフ、グループ別の棒グラフ（当月／前月）、資産推移の折れ線、貯金額の棒。

  • Recharts。重いので動的 import で分割

入力

features/entry/EntryTab.tsx

9つのサブタブ（変動費・収入・固定費・インフラ・通信費・サブスク・車・バイク・投資）でのCRUD。アプリを開いた直後の既定タブ。

  • 変動費・車・バイク・投資は「日」も任意入力できる
  • 通信費・サブスクだけは別テーブル（bundle_items）
  • 割り勘アプリへの反映ボタンもここ

目標

features/goal/GoalTab.tsx

貯蓄目標の登録と達成状況。直近6か月のペースから達成予想月を出す。

設定

features/settings/SettingsTab.tsx

カテゴリの追加・削除、投資の扱い（支出に含めるか）、CSV取込・書き出し、翌月シートの作成、月の削除。

月が主役で、日は脇役 集計・グラフ・目標はすべて月単位。entries.day は後から足した任意項目で、一覧の並べ替えと割り勘アプリへの反映にしか使わない。日が無いエントリがあっても集計は壊れない。

2. 最重要の構造 — バックエンドが2系統ある

このリポジトリには同一ロジックの独立した2実装がある。片方だけ直すとAPIの挙動がずれるため、常に同期させる。

worker/（TypeScript）backend/（Python）
フレームワークHono 4FastAPI
実行環境Cloudflare Workersローカルのみ（uvicorn）
DB本番 D1（kakei-db）backend/local.db（SQLite）
役割本番稼働ローカル開発・テスト用サンドボックス
テストvitest（3ファイル）pytest（15ファイル）

2-1. モジュールの対応

PythonTypeScript役割
backend/src/repo.pyworker/src/repo.ts全SQLアクセス。検証もここ
backend/src/aggregate.pyworker/src/aggregate.ts月次集計・KPI・前月比較
backend/src/goal.pyworker/src/goal.ts目標の達成率と達成予想月
backend/src/importer.py / exporter.pyworker/src/importer.ts / exporter.tsCSV取込・書き出し

worker/src/repo.ts のコメントに「Python版 src/repo.py の移植」と明記されている。API契約（パス・JSONの形）は両者で完全に同一。

2-2. 唯一の例外 — 割り勘アプリ連携

Cloudflare の Service Binding（Worker→Worker の直接呼び出し）を使うため、FastAPI では原理的に実装できない。以下は worker/ にしか存在しない。

  • worker/src/warikan.ts（連携クライアント）、worker/src/errors.ts
  • GET /api/warikan/status、GET /api/warikan/users、POST /api/entries/{id}/warikan、DELETE /api/entries/{id}/warikan

ただし entries.warikan_expense_id 列と /api/entries のJSONの形（割り勘ID キー）は両系統で同期している。詳細は 割り勘アプリ連携の説明書。

なぜ2つあるのか もともと Python（FastAPI）版だけだった。本番を Cloudflare Workers に載せる際、当時の Python Workers では実用に耐えなかったため TypeScript に移植した。Python版はローカルで素早く試すためのサンドボックスとして残っている。backend/worker.py と backend/wrangler.toml は廃止された Python Workers デプロイ経路の名残で、現在は未使用。

5. データベース（Cloudflare D1）

本番は D1 の kakei-db（binding は DB）。正本はD1であって backend/data/ のCSVではない — CSVを直しただけでは本番に反映されない。

5-1. テーブル

テーブル主なカラム役割
entries id, month, category, amount, source, created_at, note, day, warikan_expense_id 家計の1行。month は GLOB で YYYY-MM を強制、amount > 0。source は manual か import で、編集できるのは manual だけ
bundle_items id, kind, month, name, amount サブスク・通信費の内訳。kind は subscriptions/communications。(kind, month, name) が UNIQUE。集計時は1カテゴリに畳まれる
category_groups name, sort_order 8グループ（収入・固定費・インフラ・通信費・変動費・車・バイク・投資）。入力タブのサブタブ名と一致する
categories name, group_name, income_owner, sort_order 30カテゴリ。income_owner は夫／妻で、収入の内訳表示に使う
goals name, target_amount, source, sort_order 貯蓄目標。source は savings（累計貯金）か net_worth（純資産）
app_settings key, value 今は investment_as_expense と active_goal だけ
dashboard_months month データが0件でも月セレクタに出したい月。翌月シート作成で使う

5-2. マイグレーション

ファイル内容
0001_init.sql7テーブルの作成
0002_seed.sql8グループ・30カテゴリ・初期設定の投入
0003_add_entry_note.sqlentries.note（詳細）。空欄は許すが NULL は使わない方針で NOT NULL DEFAULT ''
0004_add_entry_day.sqlentries.day（日）。NULL = 日付なし。月末日との整合はDBではなくアプリ側で検証

worker/migrations/ と backend/migrations/ はバイト単位で同一。worker のテストは node:sqlite のインメモリDBにこのSQLを実際に適用して走るので、本番と同じスキーマで検証される。

--remote と --local を取り違えない npx wrangler d1 execute kakei-db --remote は本番、--local は開発用。削除は必ず WHERE month IN (...) で範囲を限定する。

6. 集計ロジック

6-1. 月次サマリー（monthlySummary）

すべてのエントリを月ごとに畳んで、1行 = 1か月の表を作る。ダッシュボード・グラフ・目標はすべてこの表から導かれる。

列意味
収入グループ「収入」の合計
夫収入 / 妻収入categories.income_owner で振り分けた内訳
支出収入以外の合計。investment_as_expense が false なら投資を除く
投資グループ「投資」の合計
貯金収入 − 支出
累計貯金貯金の累積
投資累計投資の累積
純資産累計貯金 + 投資累計

investment_as_expense（設定タブで切替）が、投資を「支出」に数えるかどうかを決める。これにより「貯金」の意味が変わるため、グラフも目標も一斉に変わる。

6-2. 目標（goalStatus）

  1. 現在額を取る

    目標の source が net_worth なら最新月の 純資産、そうでなければ 累計貯金。

  2. 達成率と残額

    達成率は 0〜100% にクランプ。残額は負にならない。

  3. ペースを出す

    直近6か月（PACE_WINDOW_MONTHS）の月次の積み増し（貯金、純資産目標なら 貯金+投資）の平均。

  4. 達成予想月

    残額 ÷ ペースを切り上げた月数を最新月に足す。ペースが0以下なら null（予想不能）。

6-3. 年月の正規化（dates.normalizeMonth）

CSV取込で人間が書いた表記を吸収する。空欄なら今月、1〜12 の数字だけなら今年のその月、2026年6月 / 2026/6 / 2026-6 はすべて 2026-06 になる。解釈できなければ例外。

7. API エンドポイント

/api/* は Worker（Hono）が処理し、それ以外は [assets] が SPA を返す（run_worker_first = ["/api/*"]）。エラーは FastAPI 互換の {"detail": "..."} で返す。

メソッドパス説明

レスポンスの約束 エントリとバンドルの変更系（POST/PUT/DELETE）は、更新後の全件配列を返す。ただしフロントは絞り込み条件（月・グループ）を知っているので、戻り値をそのまま画面に出さず GET で取り直す。この約束を破ると、変動費タブに家賃が混ざるようなバグになる。

認証

本番は Cloudflare Access で保護されている。多層防御として、ACCESS_ALLOWED_EMAILS が設定されていれば Worker 側でも Cf-Access-Authenticated-User-Email ヘッダを許可リストと突き合わせる（worker/src/index.ts のミドルウェア）。未設定なら素通し＝ローカル開発用。

10. ツール・実行環境・コマンド

全体を一括で実行するトップレベルのコマンドは無い。backend/ frontend/ worker/ はそれぞれ独立してテストする。

ローカル開発（FastAPI + Vite）

12. 設計上の制約と運用ルール

12-1. カテゴリ削除の保護

DELETE /api/config/categories/{name} は次の場合に400を返す。過去の集計を壊さないための保護で、両バックエンドでロジックを同期させる。

  • 実績データが1件以上ある
  • 収入内訳の特別カテゴリ（夫給与・妻給与）である
  • バンドルラベル（サブスク・通信費）である
  • そもそも存在しない

12-2. CSV取込の制限

アプリ内（設定タブ）の取込は少量の臨時追加専用。source='import' 固定で後から編集できず、bundle_items 非対応、新カテゴリも登録できない。

12-3. 月次データ運用フロー（実データ）

  1. CSVを置く

    backend/data/ に配置する。

  2. 生データで検証

    年月・カテゴリ・金額を目視と機械の両方で確認。

  3. 差分を提案

    「変更前 → 変更後 ＋ 理由」の形で出す。

  4. オーナーの承認を得る

    ここを飛ばさない。

  5. 原本を保全してから反映

    backend/backup/YYYY-MM-DD/ に原本を置いてからCSVを更新し、再検証。

  6. SQLに変換

    backend/scripts/csv_to_sql.py で INSERT 文を生成。

  7. 本番に流す

    npx wrangler d1 execute kakei-db --remote --file=<生成したsql>

  8. 再クエリで突き合わせ

    件数と合計が期待値と一致することを確認する。

12-4. データのプライバシー

実データ（家賃・投資額など）はリポジトリに入れない。backend/data/・backend/backup/・*.db・.wrangler/・.dev.vars はすべて gitignore 済み。リポジトリは公開されているため、コミット前に実額・メールアドレス・トークンが混ざっていないか確認する。

12-5. 二重実装の同期

不具合修正や挙動変更は必ず両方に入れる worker/src/*.ts だけ直すと、ローカルのFastAPIと挙動がずれて「ローカルでは直ったのに本番で再発」「その逆」が起きる。テストも両方に書く。唯一の例外は割り勘連携（Worker専用）。
